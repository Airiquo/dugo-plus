Merged App Smoke Checklist — F3 + F4 + F7 + F9 + F10a
=====================================================

What this proves: the merged branch actually works at runtime (the build and the
emulator tests do not cover the suspension gate, the donor /home IA, or the F4
map live).

Prerequisites (owner)
---------------------
1. Service-account key outside the repo, e.g. `~/.config/dugo-plus/sa-key.json`.
2. An **admin** account exists in `users/` (role admin).
3. A **hospital** account + facility — run:
     GOOGLE_APPLICATION_CREDENTIALS=~/.config/dugo-plus/sa-key.json \
       npm run create:hospital -- --email hospital@test.com --password 'Hospital1234'
   (creates the Auth login, the facility, and the profile).
4. A **donor** account (register through the app, then verify the email).
5. Deploy the merged rules/indexes (they changed: `accountActive`, `donorLocations`, D29):
     firebase deploy --only firestore:rules,firestore:indexes --project dugo-plus
6. Publish claims for the admin + hospital accounts:
     GOOGLE_APPLICATION_CREDENTIALS=~/.config/dugo-plus/sa-key.json npm run set:claims
   Then sign out/in (claims refresh) — or reload (useAuth forces one token refresh).
7. Start the app: `cd web && npm run dev`.

Run order
---------
Use two browsers/profiles (or sign out between roles).

A. Donor (F4 / F7)
   1. Sign in as the donor → lands on **`/home`** (not /donor/profile).
   2. `/donor/profile` redirects to `/home`.
   3. `/donor/requests` loads the request map (Leaflet tiles render; no blank box).
   4. `/donor/alerts` shows the inbox with the donor chrome (no admin sidebar).
   5. `/donor/privacy` opens the data-request screen (F9).
   6. Post nothing here; requests come from the hospital side.

B. Hospital (F3 / F7 / F8)
   1. Sign in as `hospital@test.com` → lands on **`/hospital/requests`**.
   2. **New request** → type/component/units/urgency → Post.
   3. Returns to the list, urgency first; **reload** → still listed.
   4. Check the posted request's `matching` in Firestore: F7 ran (tier walk).
   5. Both themes (sidebar toggle).

C. Admin (F9 / F10a)
   1. Sign in as admin → `/admin/dashboard`.
   2. `/admin/accounts` lists users; suspend a throwaway donor, then reactivate.
   3. `/admin/settings` loads and saves systemConfig (FR-041).
   4. `/admin/data-requests` lists DSRs; `/admin/profile` shows own account (FR-047).
   5. `/admin/audit-trail` → **Verify Chain** returns valid (empty or not).

D. Suspension gate (F9)
   1. Suspend a donor from `/admin/accounts`.
   2. In the donor session (after a token refresh): every built screen shows the
      **Blocked** screen; the owner can still read its own profile.
   3. Reactivate → access returns.

E. §6 four-check list (regression)
   1. Sign in → lands on the right home.
   2. Reload → saved values show.
   3. Change a field → save → reload → persisted.
   4. Unverified account still held at `/verify-email`.

Pass/fail notes
---------------
- Claims matter: without step 6, `/admin/*` and staff paths stay closed — that is
  expected, not a bug.
- Known non-blocking items: nav slugs without pages render ScreenStub
  (donor-registry, donor-matching, inventory, donations-rewards, reports).
- F10b (audit event hookups) is not built; the chain stays empty until then.

Brevo Email Delivery Check (F7 notifications)
=============================================

Goal: confirm the matching Worker actually sends match-notification email via
Brevo, and see where it stops if it does not.

How it works (worker/src/email.js, worker/src/notify.js)
--------------------------------------------------------
- Email is sent only when ALL THREE Worker secrets exist:
    BREVO_API_KEY, BREVO_SENDER_EMAIL, BREVO_SENDER_NAME
  (`isEmailEnabled(env)` returns false otherwise).
- On a match, `notifyNewMatches` writes a `notifications/{requestId}_{donorId}`
  doc (deliveryStatus: 'Pending', sentAt: null) and, if enabled, POSTs to
  `https://api.brevo.com/v3/smtp/email`. On success it sets
  `deliveryStatus: 'Sent'` + `sentAt`; on failure it logs and bumps retryCount.
- The cron `retryNotifications` retries `Pending` notifications up to
  `systemConfig.notifRetryLimit`.

STEP 1 — Are the secrets set? (names only)
------------------------------------------
  npx wrangler secret list -c worker/wrangler.toml
Expect: BREVO_API_KEY, BREVO_SENDER_EMAIL, BREVO_SENDER_NAME (plus
FIREBASE_SERVICE_ACCOUNT, FIREBASE_API_KEY, AUDIT_HASH_SECRET).
If any Brevo secret is missing -> email is off; notifications stay Pending and
only appear in the donor inbox (no mail). Set it: `npx wrangler secret put <NAME> -c worker/wrangler.toml`.

STEP 2 — Quick isolated send (proves key + sender)
--------------------------------------------------
Owner runs this (key stays out of the repo):

  curl -sS -X POST https://api.brevo.com/v3/smtp/email \
    -H "api-key: $BREVO_API_KEY" -H 'Content-Type: application/json' \
    -d '{"sender":{"email":"<BREVO_SENDER_EMAIL>","name":"<BREVO_SENDER_NAME>"},
         "to":[{"email":"<your-email>"}],
         "subject":"Dugo+ Brevo test","textContent":"If you got this, Brevo works."}'

- 2xx -> key + verified sender are good.
- 401/400 -> wrong key, or sender is not a verified sender in Brevo.

STEP 3 — Cause a real match
---------------------------
1. Ensure a donor exists that the matcher will pick:
   - role donor, status Active
   - bloodType compatible with the request
   - latitude/longitude inside a radius tier of the facility (systemConfig.radiusTiers)
   - lastDonationAt outside the component's interval
   - has an email
2. As the hospital account, post a matching request (/hospital/requests/new).
   The Worker's `/match` (or the 1-minute cron) runs and fans out.

STEP 4 — Check the system side (Firestore)
------------------------------------------
- `notifications/{requestId}_{donorId}`:
  - deliveryStatus 'Sent' + sentAt set  -> Brevo accepted it. PASS.
  - deliveryStatus 'Pending' + retryCount > 0 -> send failed; see Step 6.
  - no doc at all -> no match was produced (donor not eligible/in range).
- Donor `/donor/alerts` should list it (needs the sentAt:null write; already fixed).

STEP 5 — Check the Brevo side (definitive)
------------------------------------------
Brevo dashboard -> Transactional -> Logs / Statistics:
- "delivered" -> end-to-end PASS.
- "blocked"/"error" -> read the reason there.
Free tier caps at 300/day; over that, sends are rejected.

STEP 6 — Read the Worker logs
-----------------------------
  npx wrangler tail -c worker/wrangler.toml
While triggering a match, watch for:
- `brevo send failed { status, detail }` (worker/src/email.js) -> Brevo rejected it.
- `notification fan-out failed` (matcher) -> the notify step threw.
Anything else 5xx -> Worker/Firestore issue (e.g. SA roles/datastore.user).

Common failures
---------------
- One of the three Brevo secrets missing -> no email, Pending forever.
- Sender not verified in Brevo -> 400 from the API.
- Donor has no email / wrong bloodType / out of range / not eligible -> no match,
  so nothing to send.
- Free-tier daily cap reached -> rejected at Brevo.

What "working" looks like
-------------------------
A notification doc with deliveryStatus 'Sent' and a matching entry in the Brevo
Transactional log (delivered), and the donor seeing it in /donor/alerts.
